== A decision journey, not a scoring trick

A payment processor receives transactions with different amounts, locations,
and business contexts. Some cases are easy to explain. Others need additional
assessment. Sending every transaction to a language model would add cost and
latency while hiding a useful fact: many decisions begin with evidence that can
be calculated deterministically.

In this 75-minute experience, you play the platform and risk engineer asked to
make that decision path visible. You will inspect a deployed application,
calculate rule evidence by hand, route only an ambiguous case to an
OpenAI-compatible model, analyze a small synthetic portfolio, and challenge the
result as a reviewer would.

The goal is not to build a production fraud detector. The goal is to leave with
an explainable architecture pattern and a concrete list of controls still
required before a consequential system could be considered.

== The story you will follow

[cols="1,2,3",options="header"]
|===
|Stage |Question |Evidence you produce
|Understand |What is deployed, and where are its trust boundaries? |Namespace, workload, Route, readiness mode, and component map
|Build |Can obvious decisions be reproduced without AI? |Two hand-calculated rule scores and API contract checks
|Route |When is inference useful, and how is its contribution bounded? |An ambiguous result, formula check, model-mode evidence, and fallback interpretation
|Analyze |What happens across a mixed set of transactions? |A batch report, path distribution, latency observations, and process statistics
|Govern |What can this result prove, and what remains unresolved? |Boundary tests and a reusable review artifact with explicit open gates
|===

== Red Hat and Intel roles

Red Hat OpenShift supplies deployment, isolation, service identity, Routes,
health checks, and operational evidence. The application uses an
OpenAI-compatible provider contract so the inference endpoint can change
without rewriting the decision workflow. Intel Xeon is the CPU execution
context for the qualified model service; the learner claim is functional,
repeatable inference—not a universal latency or accuracy guarantee.

The application makes three responsibilities visible:

* *Rules* produce deterministic signals whose arithmetic can be inspected.
* *Inference* contributes a bounded score only for configured ambiguous cases.
* *Policy and people* decide whether the example is suitable for real use,
  which this lab deliberately does not claim.

== Prerequisites and lab boundaries

Launchpad provides a browser terminal authenticated to your assigned OpenShift
namespace. You need basic familiarity with command-line tools and JSON, but no
machine-learning background is required. All transaction records are fictional.
Do not paste customer, cardholder, employee, or other sensitive information
into the application.

The model may be live or the environment may use a clearly labeled simulator.
You will verify the mode before drawing conclusions. Model output is
nondeterministic, so the exercises validate structure, bounds, routing, and
evidence rather than exact prose or an exact score.

== How to use the workspaces

The same synthetic cases appear through three views:

* *Hybrid Decision Casebook* is the visual case workspace. Its guided examples
  follow the low, ambiguous, high, and adversarial cases used in the modules.
* *Terminal* is the evidence workspace. It exposes exact API responses and runs
  assertions that do not depend on the UI presentation.
* *OpenShift Console* is the platform workspace. It shows the scorer and UI
  workloads, Routes, health, configuration, and namespace boundary.

Begin a case in the Casebook, prove it in Terminal, and return to the Casebook
to interpret the result. Use the Console only at named platform checkpoints.
This keeps the lab centered on one accumulating decision journey instead of
three unrelated tabs.

== Estimated time

75 minutes. Complete the modules in order to preserve the evidence trail.
